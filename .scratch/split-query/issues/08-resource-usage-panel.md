# 08: 资源空间面板

**What to build:** 顶栏一个独立按钮点开**模态浮层**，显示本应用在手机上实际占用的存储：`条目数据`（本地条目副本的实测净字节）、`应用资源`（离线缓存的页面骨架/脚本/样式/图标/manifest 的实测字节），以及两者的一行 `合计`。从未导入过时 `条目数据` 显示「尚未导入」；某个桶读不到时该行显示「不可用」且**不显示合计**。v1 只读。

**Blocked by:** None（可立即开始）

**Status:** resolved

- [x] 新增纯 seam `format.ts`：字节 → 人类可读（KB/MB，一位小数，**不加"约"**），配自动化测试覆盖边界（0、不足 1 KB、1023 / 1024 进位、多位小数）。`CLAUDE.md` 已声明"三个纯 seam"，本票补上第三个的实现与测试
- [x] 顶栏独立按钮 → 模态浮层，可关闭（关闭按钮 + 点遮罩）
- [x] `条目数据`：打开面板时**从 IndexedDB 现读**条目，按 UTF-8 内容净字节求和（**不含** JSON 结构开销，使其可与用户的文件大小直接对照）
- [x] `应用资源`：遍历**所有** cache 求和响应字节（**不硬编码缓存名**，避免与 service worker 里的常量重复声明）
- [x] 一行 `合计`（两个实测值之和），并标注口径：仅本站点占用，不含浏览器 HTTP 缓存与系统快照，≠ 手机剩余空间变化
- [x] 从未导入 → `条目数据` 显示「尚未导入」（**不是** `0 字节`）；单桶读取失败 → 该行「不可用」且**合计整行不显示**（缺一项时合计是编造，不是求和）
- [x] 面板附一句恢复说明：文件是唯一真源，重新导入整体替换、**不累积**
- [x] 手工验证：`npm run check` 通过；面板在 `npm run build` + 预览（或线上）下数值正确 —— **dev 下无 Service Worker，`应用资源` 自然测不出，这是预期而非缺陷**
- [x] 不引入 `navigator.storage.estimate()` 探测分支，不引入 `navigator.storage.persist()`（理由见 spec 的 Out of Scope）

## 实现说明

- **单位上限 `B / KB / MB / GB`**。票面只提 KB/MB，实现加了 GB：MB→GB 是真实的精度悬崖（否则极大值会显示成 `1024.0 MB`），而 TB 对一个书签文本文件属于投机，故止于 GB。
- **进位不显示 `1024.0`**：循环退出时 `value < 1024`，四舍五入后至多恰好 1024——那不是"1024.0 KB"，而是下一级的 `1.0`。有专门测试钉住（1048575 B）。
- **按钮文案「存储」、面板标题「资源空间」**。顶栏在 iPhone 上横向紧张，故按钮用两字；面板标题用功能名。已在 390×844 视口实测顶栏一行放得下（`split-query | 导入文件 | 存储 | N 条目`）。
- **加载态「读取中…」**：测量是异步的，票面未规定；空 `<dd>` 更糟，故补一个瞬时文案。
- **`应用资源` 如实反映缓存**：它统计"此刻缓存里真实存在多少字节"，因此会随 Service Worker 生命周期变化（见下方附带发现）。
- 目标写法：`cd`/`hidden` 交互需注意——`.usage` 与 `.usage-row` 的 `display` 被 CSS 覆盖，故两者都显式写了 `[hidden] { display: none }`。

`npm run check`：tsc 无错 + **42** 个测试全绿（原 39 + format 新增 3）。

无头 Chrome（CDP、全新 profile）+ `npm run build` + 预览（走真实 Service Worker 注册路径）：

| 场景 | 结果 |
| --- | --- |
| A. 全新存储（未导入） | `条目数据 = 尚未导入`，`应用资源 = 8.5 KB`，**合计行隐藏** ✓ |
| B. 导入 `draft/demo.txt`（经 `DOM.setFileInputFiles` 走真实文件选择器路径） | 顶栏「5 条目」；`条目数据 = 167 B`，`应用资源 = 8.5 KB`，`合计 = 8.7 KB` ✓ |
| 独立复核（B） | 由已渲染条目的 DOM 重算 UTF-8 字节 = **167**，与面板读 IDB 的结果一致 ✓ |
| 缓存变化后复读 | `应用资源 = 21.9 KB`，`合计 = 22.1 KB`（167 + 22446 = 22613 → 22.1 ✓） |
| 降级（模拟 `caches.keys()` reject） | `应用资源 = 不可用`、**合计行隐藏**；恢复后回到 `8.5 KB / 8.7 KB` ✓ |
| 交互 | 点遮罩关、点面板内部**不**关、关闭按钮关、可重复打开 ✓ |
| 遮罩几何 | rect 覆盖视口，`rgba(2,6,23,0.72)`，`z-index: 20` ✓ |
| iOS 观感 | 390×844 截图确认顶栏一行放得下、面板居中；真机观感随票 07 的验收一并确认 |

`draft/demo.txt` 文件本身 211 字节，`条目数据` 167 B，差额 **44 = 22 处 CRLF × 2 字节**——该文件用 CRLF 换行，而 `条目数据` 统计的是条目内容本身，**不包含任何换行**（条目内换行与空行分隔都不算）。这是"内容净字节、可与文件大小对照"口径的直接结果：两个数之差恰是文件里的换行开销，不是估算。

## 附带发现（非本票范围，已记入 `draft.md`）

验收时发现 `应用资源` 起初只报 **8754 B**（仅 shell 预缓存），而真实应为 **22446 B**。根因**不在本票**，在 `public/sw.js` 的预热：

- 浏览器会自动请求 `/favicon.ico`，而本应用没有 favicon → **404**；
- 预热用 `cache.addAll(urls)`，而它是**全有或全无**：一条 404 即整批 reject；
- 该 reject 又被 `.catch(() => {})` 吞掉 → **预热一条都没写进去**。

逐条 `add` 复现可证：除 `/favicon.ico` 外全部成功，缓存 8754 → 22446。后果不止是数字偏小——**「一次在线即离线」不成立**（首次在线访问后 JS/CSS 未入缓存，需第二次加载），这正是票 06 的离线承诺。修法见 `draft.md`。
